    The short path

    Five topics for everyday Git.

    01How Git saves your work

    Your files, the next commit, and saved history.

    • The working tree is the folder you edit.
    • The staging area holds the file versions for your next commit.
    • The repository stores your commits.

    git add copies a file into staging. git commit saves that snapshot. A commit stays on your computer until you push it.

    02Set up a project

    Set your identity once, then choose an existing project or a new one.

    With Git installed, set the name and email that will appear on your commits. Replace anything in <angle brackets> with your own value, leaving out the brackets.

    $ git config --global user.name "Your Name"
$ git config --global user.email "you@example.com"

    Choose one of the two paths below.

    Join an existing project

    Copy the repository URL from its website. Cloning downloads the project and remembers that address as origin, so you can fetch and push later.

    $ git clone <repository-url>
$ cd <repository-folder>

    Start a new project

    Open your project folder in a terminal. For a folder that is not already a Git repository, this starts its history with a branch named main.

    $ git init -b main

    Create or edit a file, such as README.md, then make your first commit using Save a change below. You need that first commit before you can push.

    When you are ready to put the project online, create an empty repository on your Git hosting website. Leave its README, license, and .gitignore options unchecked: you already started the history on your computer. Copy its URL, then run:

    $ git remote add origin <repository-url>
$ git push -u origin main

    origin is the saved name for that URL. -u connects your local branch to its remote branch, so later git pull and git push know which one to use. Your hosting service may ask you to sign in.

    03Save a change

    Edit, inspect, stage, then commit.

    After editing a file, check what changed, choose what to save, and make a commit.

    $ git status
$ git diff
$ git add <file>
$ git diff --staged
$ git commit -m "Describe your change"
    • git status lists changed and untracked files.
    • git diff shows unstaged edits to tracked files. It does not show the contents of new, untracked files.
    • git add <file> stages the version of that file you want to save.
    • git diff --staged shows what the next commit will save, including newly added files.
    • git commit -m "Describe your change" saves the staged changes in your local history.

    If you edit a file after staging it, run git add again to include the newer edits. Keep passwords and API keys out of commits.

    StashSave unfinished edits before you change branches.

    The -u option includes untracked files, but not ignored files.

    $ git stash push -u -m "Pause this task"
$ git switch <other-branch>

    Finish and commit the other task. Then return to your original branch and restore the saved edits.

    $ git switch <original-branch>
$ git stash pop

    If pop reports a conflict, the stash stays available. Resolve the conflict before you continue.

    Read the full stash guide.

    04Use a branch and share it

    A branch lets you work on a change without moving main forward.

    Start from an up-to-date main, then create a branch for your change. Commit or stash unfinished edits first. If pull --ff-only fails, your branch needs attention before you continue; the fetch and pull example below explains why.

    These examples use main as the shared branch. If your project uses another name, substitute it. For a new project, finish the first commit and push from the setup section before continuing.

    $ git switch main
$ git pull --ff-only
$ git switch -c <branch-name>

    Edit your files and commit with the previous steps. Then push your branch.

    $ git push -u origin <branch-name>

    Open the repository website and create a pull request. Ask for review before you merge.

    After your pull request is merged

    The website has updated the shared branch; your local copy still needs that update. Commit or stash any unfinished edits, then return to main and pull.

    $ git switch main
$ git pull --ff-only

    Once the pull succeeds and you have checked that your change is in main, you can delete the finished local branch if you no longer need it.

    $ git branch -d <branch-name>

    This does not delete the branch on the website. If Git refuses because it considers the branch unmerged, keep it while you check. A squash merge can cause this because it gives your changes a new commit ID; do not switch to force deletion just to clear the message.

    Fetch versus pullCheck remote changes before you update your files.

    Fetch downloads remote commits and updates remote references. It does not change your working files.

    Pull also fetches, then updates your current branch. The --ff-only option stops if that update needs a merge.

    This example assumes you are on main with origin/main as its upstream. The log command lists remote commits absent from your current history.

    $ git fetch origin
$ git log --oneline HEAD..origin/main
$ git pull --ff-only

    Stop if pull refuses. Use the full guide to choose the next step.

    Read the full fetch and pull guide.

    Merge conflictsChoose the final text when Git cannot combine edits.

    Commit or stash your edits before a merge. This example merges another branch into your current branch.

    $ git merge <branch-name>
$ git status

    If Git reports conflicts, open each conflicted file. A text conflict can look like this:

    <<<<<<< HEAD
Welcome to our app.
=======
Welcome to our project.
>>>>>>> feature/welcome

    For this merge, the text above ======= is from your current branch. The text below it is from the branch you are merging in. Decide what the file should say: keep either version or write a combination.

    For example, if you want to keep the second wording, replace the whole marked block with:

    Welcome to our project.

    Remove the <<<<<<<, =======, and >>>>>>> lines. Check the rest of the file for more conflicts and test the result before marking it resolved.

    Stage each resolved file, then finish the merge.

    $ git add <resolved-file>
$ git commit --no-edit

    To cancel an unfinished merge instead, run git merge --abort. This command does not cancel a rebase.

    Read the full merge conflict guide.

    WorktreesUse two branches in separate folders.

    Use a second folder for a review or urgent fix. Your current edits stay in the first folder.

    Both folders share commit history, but each has its own files and staging area. This example creates hotfix from your local main.

    $ git worktree add -b hotfix ../hotfix main
$ git worktree list

    Commit the work in the second folder before you remove it. The branch and its commits stay in the repository.

    $ git worktree remove ../hotfix

    Read the full worktree guide.

    05Unstage or undo a commit

    Unstage a file, or reverse a commit.

    Staged the wrong file? Unstage it. Your edits stay.

    $ git restore --staged <file>

    Need to undo a commit? Commit your other edits first. Find the commit ID, then create a new commit that reverses it.

    $ git log --oneline
$ git revert --no-edit <commit-id>

    Avoid --hard and --force while you learn. They can remove work.

    01How Git stores work

    Git stores a snapshot of your files. It keeps three places for that work. Each command moves work from one place to another.

    What version control is (and the problem it solves)

    Every project eventually ends up with folders like report-final.docx, report-final-v2.docx and report-final-v2-REALLY-final.docx. That is version control done by hand. It breaks down fast: you cannot tell what changed between versions, you cannot tell why it changed, and two people editing the same files will overwrite each other.

    A version control system (VCS) records the history of a set of files so you can answer three questions at any time: what changed, who changed it and why. It also lets you go back to any earlier state. Git is by far the most widely used VCS. Linus Torvalds wrote it in 2005 to manage the Linux kernel, so it was designed from the start to be fast, to work offline, and to handle thousands of contributors working in parallel.

    Saved states stay

    Git keeps each commit. You can read it, compare it, or restore it years later.

    A branch is a safe test

    You try an idea on a branch. If it works, you merge it. If it fails, you delete the branch. The other work stays.

    People can work at the same time

    Git combines their work. It shows the lines that really conflict.

    Each change has an author

    A commit stores the author, the time, and the message. git log and git blame show that record.

    Plain text works best

    Git works best with plain-text files (source code, Markdown, config, SVG, CSV), because it can show you line-by-line differences. It can store binary files like images or PDFs, but it can only tell you that they changed, not how. For very large binaries, look at Git LFS.

    Centralized vs distributed

    Older systems like Subversion (SVN), CVS and Perforce are centralized: one server holds the history, and developers check out a working copy from it. Committing, viewing history and branching all need a connection to that server.

    Git is distributed. When you clone a repository you get the entire history: every commit, every branch, every version of every file. Your laptop has a complete, independent repository. Commits, logs, diffs and branches are local operations, so they are instant and work on a plane. You share work by exchanging commits with other repositories, usually through a shared remote that everyone agrees to treat as the hub.

    Centralized

    One source of truth on a server.

    • Most operations need the network
    • Commits go straight to the shared server, so experiments are public
    • Branching is often heavy and avoided
    • The server is a single point of failure

    Distributed (Git)

    Every clone is a full repository.

    • Commit, branch, diff and log all run locally and instantly
    • You decide when to share (git push)
    • Branches are cheap, so you use them for everything
    • Every clone is effectively a backup

    Git stores snapshots, not diffs

    Many older systems store a base version of each file plus a chain of changes (deltas) over time. To rebuild version 4 they start from version 1 and apply every delta in order.

    Git thinks differently. Each commit records a snapshot of what all your tracked files looked like at that moment. That sounds wasteful, but Git stores file contents by their hash. If a file did not change, the new snapshot just points to the same stored content as before. Nothing is duplicated.

    This design is why switching branches, comparing any two commits or checking out an old version is fast in Git: each commit already knows the full state of the project.

    What about disk space?

    Git also compresses the stored objects. It periodically packs objects into packfiles and delta-compresses similar content inside them. That is a storage optimization only. The model you work with is always "each commit is a full snapshot".

    The three areas: working tree, staging area, repository

    This is the most important idea in this chapter. Your files live in three places at once, and most everyday commands just move content between them.

    Working tree

    The actual files in your project folder. You edit them with your editor like any other files. Git watches them but does not save anything on its own.

    Staging area (index)

    A draft of your next commit. It is stored in .git/index. git add copies the current version of a file into it.

    Repository

    The .git directory: every commit ever made, plus branches and tags. git commit turns the staging area into a permanent snapshot here.

    Why have a staging area at all? It lets you choose what goes into a commit. Say you fixed a bug and also reformatted an unrelated file. You can stage only the bug fix, commit it with a clear message, and then commit the formatting separately. Clean, focused commits make history easier to read, review and revert.

    # edit two files, stage only one of them
$ git add app.js
$ git status
On branch main
Changes to be committed:
  (use "git restore --staged <file>..." to unstage)
        modified:   app.js

Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git restore <file>..." to discard changes in working directory)
        modified:   style.css
$ git commit -m "Fix crash when cart is empty"
[main e41b7c2] Fix crash when cart is empty
 1 file changed, 3 insertions(+), 1 deletion(-)
    Three places

    The working tree holds the files you edit. The staging area holds the next commit. The repository holds the saved commits. git add copies a file into the staging area. git commit saves that staging area. Files you do not add stay in the working tree.

    The index is a full snapshot

    A common misconception is that the staging area only holds "the changes". It holds the complete set of files for the next commit. Right after a commit, the index matches that commit exactly. git add overwrites the staged copy of a file with the current version from your working tree.

    The life cycle of a file

    From Git's point of view, every file in your working tree is in one of two broad groups. Tracked files are files Git knows about, because they were in the last commit or have been staged. Untracked files are everything else, such as a new file you just created or a build artifact. Tracked files can be in three further states:

    Untracked
    Exists on disk but Git does not know about it yet. Untracked files will not be committed until you git add them.
    Unmodified
    Tracked and identical to the version in the last commit. Nothing to do.
    Modified
    Tracked and different from what is staged, but the change is not staged yet.
    Staged
    The current version has been copied into the index and will go into the next commit.

    You can watch a file move through these states with git status:

    $ echo "# Notes" > notes.md
$ git status --short
?? notes.md                  # untracked
$ git add notes.md
$ git status --short
A  notes.md                  # staged (new file)
$ git commit -m "Add notes"
[main 5d20a8f] Add notes
 1 file changed, 1 insertion(+)
 create mode 100644 notes.md
$ git status --short          # unmodified: prints nothing
$ echo "- buy milk" >> notes.md
$ git status --short
 M notes.md                  # modified, not staged
$ git add notes.md
$ git status --short
M  notes.md                  # staged
    Going backwards

    Modified but you want the old version back? git restore notes.md (older Git: git checkout -- notes.md). Staged but you want to unstage? git restore --staged notes.md (older Git: git reset HEAD notes.md). Both are covered in depth in the undo chapter.

    What a commit is

    A commit is a small, immutable record stored in .git/objects. It contains:

    • A pointer to a tree: the snapshot. A tree is like a directory listing that maps names to blobs (file contents) and to other trees (subdirectories).
    • Parent pointer(s): the hash of the commit(s) this one was built on. The very first commit has no parent, a normal commit has one, and a merge commit has two or more.
    • Metadata: author (who wrote the change, and when), committer (who recorded it, and when) and the commit message.

    Git hashes all of that together and the result is the commit's ID: a 40-character SHA-1 hash such as c31b9e2f4a7d58e0b6c1f3a9d2e47b8c05f1a6d3. You will usually see it shortened to the first 7 or so characters (c31b9e2). Any unambiguous prefix works in commands.

    You can look at the raw object yourself. git cat-file -p prints any object in readable form:

    $ git cat-file -p HEAD

parent 7a9e05c8d1b34f62e9a0c7d5b8f3e1a24c6d9b07
author Ada Lovelace <ada@example.com> 1791885600 +0200
committer Ada Lovelace <ada@example.com> 1791885600 +0200

    Why the hash matters

    Because the ID is a hash of the commit's content, and that content includes the parent's ID, every commit effectively seals its entire history. Change one byte in an old commit and its hash changes. That changes its child's parent pointer, so the child's hash changes too, and so on all the way to the tip. That gives you three useful guarantees:

    • Integrity: corruption or tampering is detectable. If two people have the same commit hash, they have exactly the same history.
    • Immutability: commits are never edited. Commands that "rewrite history" (amend, rebase) create new commits with new hashes and move the branch label to them.
    • Deduplication: identical file contents always produce the same blob hash, so they are stored once.
    SHA-1 and SHA-256

    Git has used SHA-1 historically, with collision detection hardening. Newer Git can create repositories that use SHA-256 (git init --object-format=sha256), and the ecosystem is gradually moving that way. Everything in this guide works the same either way. SHA-256 hashes are just 64 characters long.

    Git vs GitHub, GitLab and friends

    Beginners often mix these up. Git is the version control tool: a program on your computer that manages repositories. GitHub, GitLab, Bitbucket, Codeberg and Azure DevOps are hosting services. They run Git on servers so teams have a shared remote, and they add collaboration features around it.

    Git

    Free, open-source command-line tool.

    • Commits, branches, merges, history
    • Works fully offline
    • Talks to any remote over HTTPS or SSH
    • Does not need an account anywhere

    GitHub / GitLab / Bitbucket

    Services that host Git repositories.

    • Pull requests / merge requests and code review
    • Issues, wikis, project boards
    • CI/CD (GitHub Actions, GitLab CI)
    • Access control, forks, web UI

    You can use Git without any of them, for example in a private repo on your own machine or a bare repo on a server you control. Switching hosts is easy because the history is just Git: push it to a new remote and it is all there.

    Pull request is not a Git command

    "Pull request" (GitHub, Bitbucket) and "merge request" (GitLab) are features of the hosting service, not of Git itself. They are a request to merge one branch into another, plus a discussion page.

    First-time setup with git config

    Git records your name and e-mail in every commit you make, so set those first. Everything is configured with git config.

    # identity: goes into every commit (use the e-mail your Git host knows)
$ git config --global user.name "Ada Lovelace"
$ git config --global user.email "ada@example.com"

# new repos start on "main" instead of "master"
$ git config --global init.defaultBranch main

# editor for commit messages, rebase todo lists, etc.
$ git config --global core.editor "code --wait"     # VS Code
$ git config --global core.editor "nano"            # or nano / vim / ...

# what "git pull" does when your branch and the remote have diverged
$ git config --global pull.rebase true               # rebase local commits on top
# (or: pull.rebase false to merge, or pull.ff only to refuse unless fast-forward)
    user.name / user.email
    Your identity in commits. Use the same e-mail as your GitHub/GitLab account so commits link to your profile. Hosts offer a private "noreply" address if you do not want your real e-mail public.
    init.defaultBranch
    The name of the first branch in a new repository. main is the modern convention and what GitHub, GitLab and this guide use.
    core.editor
    Opened whenever Git needs text from you, e.g. git commit without -m. GUI editors need a "wait" flag (code --wait, subl -w) so Git waits until you close the tab.
    pull.rebase
    Modern Git refuses to guess when git pull finds diverged history ("fatal: Need to specify how to reconcile divergent branches"). Set it once: true rebases your local commits onto the remote ones, false creates a merge commit. The collaboration chapter explains the trade-off.
    core.autocrlf
    Line-ending conversion. Windows uses CRLF, macOS and Linux use LF. See below.

    Line endings on Windows

    If Windows and macOS/Linux users share a repo without a line-ending policy, every line of a file can appear "changed" just because CRLF became LF. The usual setup:

    # Windows: convert LF to CRLF on checkout, back to LF on commit
$ git config --global core.autocrlf true
# macOS / Linux: convert CRLF to LF on commit, never on checkout
$ git config --global core.autocrlf input
    Even better: .gitattributes

    Personal settings vary per machine. A .gitattributes file committed to the repo makes the policy apply to everyone. A single line, * text=auto eol=lf, normalizes text files to LF in the repository regardless of who commits them.

    Changing user.name or user.email only affects future commits. Existing commits keep the identity they were made with, because that identity is part of their hash.

    Check yourself

    What are the three areas in Git, and which commands move content between them?

    The working tree (files on disk), the staging area / index (the draft of the next commit) and the repository (.git, all commits). git add copies working-tree content into the index, and git commit turns the index into a new commit. Going back, git restore <file> overwrites the working tree from the index, git restore --staged <file> overwrites the index from HEAD, and git switch updates both from another commit.

    If Git stores a full snapshot per commit, why does not a repository with 10,000 commits use 10,000 times the disk space?

    File contents are stored as blobs addressed by their hash. A file that did not change between commits has the same hash, so the new snapshot just points to the existing blob. On top of that, Git packs objects into packfiles with zlib and delta compression. Snapshots are the logical model, not a literal copy of every file.

    You edit an old commit's message with a rebase. Why do all the commits after it get new hashes?

    A commit's hash is computed from its content, which includes the message and the parent's hash. Changing the message gives the commit a new hash. Its child now has a different parent pointer, so the child's hash changes too, and so on up to the branch tip. That is why "rewriting history" really means creating new commits.

    Your global config has your personal e-mail, but this one repository should use your work e-mail. How do you set that, and how do you check which one wins?

    Inside the repository run git config user.email "you@work.com". Without a flag, git config writes to the local .git/config, and local overrides global. Check the effective value with git config user.email, or see every source with git config --list --show-origin.

    02The daily loop

    Most days you do one loop. You edit files, see the change, stage the lines you want, and commit.

    Here is the loop at a glance. Everything below expands on one of these arrows.

    Creating a repository: git init

    git init turns the current directory into a Git repository. It does not touch your existing files. It only creates a hidden .git subdirectory, which is the repository.

    $ mkdir recipes && cd recipes
$ git init
Initialized empty Git repository in /home/ada/recipes/.git/
$ git status
On branch main

No commits yet

nothing to commit (create/copy files and use "git add" to track)
$ ls -A .git
HEAD  config  description  hooks  info  objects  refs
$ cat .git/HEAD
ref: refs/heads/main

    You can also run git init my-project to create the directory and initialize it in one step, or run git init inside a folder that already has code in it. Nothing is tracked until you git add and commit.

    objects/
    The object database: every blob, tree and commit, stored by hash.
    refs/
    Branches (refs/heads/), tags (refs/tags/) and remote-tracking branches (refs/remotes/). Each is a tiny file containing a commit hash.
    HEAD

    Your files stay, but every commit, branch and stash is gone unless it exists in another clone. Never delete .git to "fix" something.     Some files should never be committed: dependencies you can reinstall, build output, logs, secrets, editor settings and OS clutter.     Global and local-only ignores

    Files that are specific to you, such as your editor's swap files or .DS_Store, belong in a global ignore file rather than in every project's .gitignore. For one-off, uncommitted ignores in a single repo, use .git/info/exclude.

    Git does not record renames

    A commit just stores snapshots, and there is no "rename" field. Git detects renames when it shows diffs and logs, by noticing that a deleted file and an added file have similar content (50% similar by default). Use git log --follow <file> to trace a file's history across renames. Tip: rename in one commit and make big edits in the next, so detection stays reliable.

    git rm refuses to lose work

    If the file has changes that are not committed, git rm stops with an error rather than deleting them. git rm -f overrides that and throws those changes away for good.

    03Branches and merge

    A branch is a name that points at one commit. You move that name. Merge and rebase use that same idea.

    A branch is just a movable pointer

    In many older version-control systems a branch is a heavyweight copy of the project. In Git, a branch is nothing more than a name that points at one commit. Physically it is a small file (or an entry in .git/packed-refs) containing a 40-character commit hash. Creating a branch writes one tiny file. It does not copy a single source file.

    Because every commit records its parent, a pointer to the newest commit is enough to reach the whole history behind it. "The feature branch" really means "the commit feature points at, plus everything reachable from it".

    You can see this for yourself. Nothing here is special: the branch is literally a text file holding a hash.

    Three places

    Commits are permanent, immutable snapshots. Branches are sticky notes you can peel off and stick on any commit. Almost every branch command (create, move, delete, merge, reset) is just sticky-note management. Deleting a branch never deletes commits directly. It only removes a name. Commits that nothing points at anymore are eventually garbage-collected.

    HEAD and how it moves when you commit

    HEAD answers the question "where am I?". Normally it is a symbolic reference: it does not hold a hash, it holds the name of a branch (ref: refs/heads/main). That branch is your current branch.

    When you run git commit, Git creates the new commit with the current tip as its parent, and then moves the branch HEAD points at forward to the new commit. HEAD itself does not change: it still says "main", but "main" now means a newer commit. Other branches stay exactly where they were.

    Switching branches is the other half of the story. git switch feature rewrites .git/HEAD to ref: refs/heads/feature and updates your working tree and index to match that commit. From then on, new commits advance feature and leave main alone, which is how history forks:

    -M forces the rename even if the target name already exists (overwriting that branch, so be careful). Renaming locally does not rename anything on a remote. You push the new name and delete the old one there.

    Deleting: -d vs -D

    git branch -d is the safe delete: Git refuses if the branch has commits that are not merged into its upstream (or into HEAD when there is no upstream). -D (short for --delete --force) deletes regardless.

    $ git branch -d feature/search

$ git branch -d experiment
error: the branch 'experiment' is not fully merged
hint: If you are sure you want to delete it, run 'git branch -D experiment'
$ git branch -D experiment
Deleted branch experiment (was c3d4e5f).

    The "(was c3d4e5f)" message is your safety net. If you deleted the wrong branch, git branch experiment c3d4e5f brings it straight back. If the message has scrolled away, git reflog still knows where the branch used to point.

    You cannot delete the branch you are currently on. Switch away first.

    If your edits do not touch files that differ between the two branches, Git simply carries them along to the new branch. If they would be overwritten, Git refuses rather than losing your work:

    Detached HEAD

    Usually HEAD points at a branch. In detached HEAD state, HEAD points directly at a commit hash instead. Nothing is broken. You are simply not "on" any branch. It happens when you check out something that is not a local branch name:

    • a specific commit: git switch --detach 7c2e0a9 or git checkout 7c2e0a9
    • a tag: git checkout v1.4.0
    • a remote-tracking branch: git checkout origin/main
    • automatically, in the middle of a rebase or a git bisect session

    Getting out safely

    1. Want to keep what you did?

      While still detached, give it a name: git switch -c parser-spike. HEAD is now attached to a real branch at the same commit and nothing is at risk.

    2. Already switched away?

      Use the hash from the warning: git branch parser-spike c3d4e5f. Lost the warning too? Run git reflog and look for the "commit:" entries made while detached.

    3. Just looking around?

      git switch - or git switch main takes you back. Nothing was changed, nothing is lost.

    Rule of thumb

    Detached HEAD is for reading history: inspecting an old release, running a bisect, building a tag. The moment you want to commit, create a branch first with git switch -c.

    Merging: fast-forward vs three-way

    git merge <branch> brings the work of another branch into the branch you are on. Always check where HEAD is first: you switch to the receiving branch, then merge the other one in. Git picks one of two very different strategies depending on the shape of the history.

    Fast-forward: nothing to combine

    If the current branch has not moved since the other branch split off (it is a direct ancestor of the other branch), there is nothing to reconcile. Git moves the pointer forward and creates no new commit.

    $ git switch main
$ git merge feature
Updating e9b4c1d..4f8a2b7
Fast-forward
 src/login.js   | 42 ++++++++++++++++++++++++++++++++++++++++++
 src/styles.css |  8 ++++++++
 2 files changed, 50 insertions(+)
 create mode 100644 src/login.js

    Three-way merge: both sides moved

    If both branches gained commits after they split, a fast-forward is impossible: neither tip contains the other. Git then performs a three-way merge using three snapshots: the two tips and their merge base (the most recent common ancestor). For each file, Git compares each tip to the base. A change made on only one side is taken automatically. Identical changes on both sides are fine. Different changes to the same lines are a conflict.

    $ git switch main
$ git merge feature/login

    What is "ort"?

    ort ("Ostensibly Recursive's Twin") has been Git's default merge strategy since 2.34, replacing recursive. It produces the same kind of results, faster and with fewer odd edge cases. You will rarely need to choose a strategy yourself.

    Controlling merges: --no-ff, --ff-only, --squash

    By default Git fast-forwards when it can and creates a merge commit when it must. Three flags let you override that.

    --no-ff. Always make a merge commit

    Even when a fast-forward is possible, create a merge commit. The feature's commits stay visibly grouped as a "bubble" in the graph, and the whole feature can be reverted by reverting a single merge commit. Popular for long-lived integration branches.

    --ff-only. Fast-forward or fail

    Only succeed if no merge commit is needed. If the branches have diverged, stop with an error so you can decide (often: rebase first). Great as a default for updating main from origin/main.

    --squash. One commit, no merge link

    Apply the combined changes of the branch to your working tree and index, but do not commit and do not record a second parent. You then commit once. Clean history, but Git no longer knows the branch was merged.

    $ git merge --no-ff feature/login

$ git merge --ff-only feature/pricing
fatal: Not possible to fast-forward, aborting.
$ git merge --squash feature/search

 1 file changed, 57 insertions(+)
    Squash side effect

    After a squash merge, the original branch is not considered merged: git branch -d feature/search will refuse, and you need -D. The same applies after a "Squash and merge" on GitHub or GitLab. Also, never keep committing on a branch after it has been squash-merged. Merging it again will replay old changes and often conflict.

    To make a preference permanent, use configuration: git config --global merge.ff only makes plain git merge behave like --ff-only, and merge.ff false behaves like --no-ff.

    Merge conflicts in depth

    A conflict is not an error. It is Git saying "both sides changed the same thing differently, and I will not guess". Conflicts happen when, relative to the merge base:

    • both branches changed the same lines (or adjacent lines) of a file in different ways,
    • one branch modified a file and the other deleted it (modify/delete),
    • both branches added a file at the same path with different contents (add/add),
    • a file was renamed differently on each side (rename/rename).

    Changes to different parts of the same file merge cleanly. Git works line by line, not file by file.

    Ours and theirs flip during a rebase

    In a rebase, Git is replaying your commits on top of the other branch, so "ours" is the branch you are rebasing onto (e.g. main) and "theirs" is your own commit being replayed. It trips up almost everyone at least once.

    Rebase basics

    Merging joins two lines of history with a merge commit. Rebasing takes a different approach: it moves your branch so that it starts from a new base, as if you had begun your work from the latest main.

    Mechanically, git rebase main (run while on feature):

    1. Finds the merge base

      The commit where feature split from main.

    2. Saves your commits as patches

      Every commit on feature that is not on main.

    3. Re-applies them one by one on top of main

      Each replayed commit is a brand-new commit: same message, same author, same change, but a different parent, so a different hash.

    4. Moves the branch pointer

      feature now points at the last new commit. The originals are left behind, unreferenced.

    Merge vs rebase, and the golden rule

    Both commands integrate changes from one branch into another, and both produce the same final files when there are no conflicts. They differ in the history they leave behind.

    git merge

    Joins histories with a merge commit. Nothing existing is changed.

    • Non-destructive: existing commits keep their hashes.
    • Safe on shared branches. Never requires a force push.
    • History shows what really happened, including parallel work.
    • Conflicts are resolved once, in one place.
    • Frequent "merge main into feature" commits can clutter the graph.

    git rebase

    Replays your commits on a new base, producing a linear history.

    • Rewrites commits: new hashes, the originals are abandoned.
    • Clean, straight history that is easy to read and bisect.
    • Lets you tidy commits before sharing them (with -i).
    • Conflicts may need resolving once per replayed commit.
    • Needs a force push if the branch was already pushed.

    A common, pragmatic workflow: rebase your own local feature branch onto the latest main to keep it current and tidy, then merge it into main (often via a pull request). You get a readable history without ever rewriting anything other people depend on.

    The golden rule of rebasing

    Never rebase commits that other people already have, i.e. anything pushed to a shared branch such as main, develop or a teammate's branch.

    Rebasing replaces those commits with copies. Everyone else still has the originals, so their next pull mixes old and new versions of the same work: duplicate commits, repeated conflicts, and possibly lost changes when someone force-pushes over someone else. Rebasing a branch only you work on is fine. If you already pushed it, update the remote with git push --force-with-lease (see force pushing in the next chapter) and make sure nobody else built on it.

    Check yourself

    You run git branch experiment and then git commit. Which branch moves?

    The branch you were already on (for example main). git branch only creates the pointer. It does not switch. HEAD still points at main, so the commit advances main and experiment stays behind. Use git switch -c experiment to create and switch in one step.

    When does git merge fast-forward, and when does it create a merge commit?

    It fast-forwards when the current branch is an ancestor of the branch being merged (the current branch has no commits of its own since they split), so the pointer can simply slide forward. If both branches have new commits, it performs a three-way merge using the merge base and records a merge commit with two parents. --no-ff forces a merge commit. --ff-only refuses anything but a fast-forward.

    You committed twice in detached HEAD state and then switched to main. Are those commits gone?

    Not yet. They still exist in the object database, just without a branch pointing at them. Use the hash from Git's "you are leaving 2 commits behind" warning, or find it in git reflog, then run git branch rescue <hash>. Unreachable commits are only removed by garbage collection once their reflog entries expire, which by default takes at least 30 days.

    Why should you not rebase main after it has been pushed?

    Rebasing creates new commits with new hashes and abandons the originals. Collaborators already have the originals, so their history and yours now disagree: pulls produce duplicated commits and repeated conflicts, and pushing the rewritten branch requires a force push that can wipe out others' work. Rebase only commits that nobody else has yet.

    04Remotes

    A remote is another copy of the repository. Fetch, pull, and push move commits between your copy and that copy.

    What a remote is

    A remote is a named bookmark for another repository's URL. That is all. It might live on GitHub, GitLab, a company server, or even another folder on your disk. Git never talks to a remote on its own: only git fetch, git pull, git push (and git clone, git ls-remote) touch the network. Everything else (commit, branch, log, merge) is purely local, which is why Git is fast and works offline.

    When you git clone a repository, Git automatically creates a remote called origin pointing at the URL you cloned from. "origin" is only a convention. It has no special powers, and you can rename it or add more remotes.

    Remote-tracking branches

    Your local repository keeps a read-only snapshot of where the remote's branches were the last time you talked to it. These are remote-tracking branches, named <remote>/<branch>: origin/main, origin/feature/search, and so on. They live under refs/remotes/.

    There are therefore three different "mains" to keep apart:

    main

    Your local branch. Moves when you commit, merge, reset. Nobody else can move it.

    origin/main

    Your local, read-only copy of the server's main as of your last fetch/pull/push. Only moves when you talk to the server.

    main on the server

    The real branch on GitHub. Teammates move it by pushing. You cannot see it change until you fetch.

    You can read remote-tracking branches like any other ref: git log origin/main, git diff main origin/main, git show origin/feature/search:README.md. You cannot commit to them. If you check one out, you get a detached HEAD. To work on a remote branch, create a local branch from it. git switch does that automatically when the name matches exactly one remote branch:

    git fetch

    "Show me what is new." Download only.

    • Updates origin/* but leaves local branches unchanged.
    • Never conflicts, never changes your files.
    • Lets you inspect before integrating (git log main..origin/main).
    • git fetch --all fetches every remote.

    git pull

    "Bring my branch up to date now." Download and integrate.

    • Fetch, then merge (or rebase) the upstream into the current branch.
    • Can create merge commits or stop on conflicts.
    • Only affects the current branch.
    • Behaviour depends on pull.rebase / pull.ff config.

    Divergent branches and reconciling them

    The interesting case is when both sides moved: you committed locally, and someone pushed to the server. Your main and origin/main have diverged. A fast-forward is impossible, so Git has to merge or rebase.

    Since Git 2.27, a plain git pull in this situation asks you to choose a strategy, and modern versions refuse to continue until you do:

    $ git pull

hint: You can do so by running one of the following commands sometime before
hint: your next pull:
hint:
hint:   git config pull.rebase false  # merge
hint:   git config pull.rebase true   # rebase
hint:   git config pull.ff only       # fast-forward only
hint:
hint: You can replace "git config" with "git config --global" to set a default
hint: preference for all repositories. You can also pass --rebase, --no-rebase,
hint: or --ff-only on the command line to override the configured default per
hint: invocation.
fatal: Need to specify how to reconcile divergent branches.

    Nothing was lost: the fetch already happened, only the integration step stopped. Pick one approach:

    Setting / flagResult when divergedGood for

    Which one should I pick?

    Rebasing on pull is safe as long as the commits being replayed are only yours and unpushed, which is exactly the case in this scenario. Many teams use pull.rebase true globally. If you prefer to look before you leap, use pull.ff only and run git fetch + git rebase origin/main or git merge origin/main yourself.

    Because Git compares your branch with its upstream's last fetched position, ahead/behind numbers are only as fresh as your last fetch. Run git fetch first when it matters.

    Rejected pushes and force pushing

    If someone pushed to the branch since you last fetched, your push is not a fast-forward and the server rejects it. This is Git protecting their work, not an error in yours.

    $ git push
To github.com:acme/widget.git
 ! [rejected]        main -> main (fetch first)
error: failed to push some refs to 'github.com:acme/widget.git'
hint: Updates were rejected because the remote contains work that you do not
hint: have locally. This is usually caused by another repository pushing to
hint: the same ref. If you want to integrate the remote changes, use
hint: 'git pull' before pushing again.
hint: See the 'Note about fast-forwards' in 'git push --help' for details.

    If you had already fetched, the message reads (non-fast-forward) and says the tip of your branch is behind its remote counterpart. Same cause, same fix:

    1. Integrate the remote work

      git pull --rebase (or a merge-based git pull). Your commits now sit on top of theirs.

    2. Resolve any conflicts

      Exactly as in the previous chapter: edit, git add, git rebase --continue (or git commit for a merge).

    3. Run the tests, then push again

      Now your tip contains the server's tip, so git push is a fast-forward and is accepted.

    $ git pull --rebase
Successfully rebased and updated refs/heads/main.
$ git push
To github.com:acme/widget.git
   d4c3b2a..9b8a7c6  main -> main

    When you really do need to overwrite: force pushing

    After you rebase, amend or squash commits that were already pushed (typically your own feature branch during review), your local branch and the remote have diverged on purpose. Pulling would bring the old commits back. Here you want to replace the remote branch, which requires a force push.

    git push --force-with-lease

    "Overwrite the remote branch, but only if it is still where I last saw it (my origin/branch)."

    • If someone pushed in the meantime, the push is rejected with (stale info).
    • Protects against overwriting work you have never seen.
    • Add --force-if-includes (Git 2.30+) to also catch the case where a background fetch updated origin/branch without you integrating it.

    git push --force

    "Make the remote branch equal to mine, no questions asked."

    • Blindly replaces whatever is on the server.
    • Any commits pushed by others since your last fetch are dropped from the branch.
    • Almost never the right choice. Use --force-with-lease instead.
    $ git rebase main
Successfully rebased and updated refs/heads/feature/search.
$ git push --force-with-lease
To github.com:acme/widget.git

# if a reviewer had pushed a fixup in the meantime:
$ git push --force-with-lease
To github.com:acme/widget.git
 ! [rejected]        feature/search -> feature/search (stale info)
error: failed to push some refs to 'github.com:acme/widget.git'
    Never force push shared branches

    Do not force push main, develop, release branches, or any branch other people commit to. It rewrites history everyone else depends on and can silently delete their commits from the branch. Most hosting providers let you protect such branches so force pushes are rejected outright. Turn that on.

    Force pushing your own feature branch after a rebase is normal, but always use --force-with-lease, and tell co-authors of the branch before you do it.

    Undoing a bad force push

    The overwritten commits still exist in the reflog of whoever had them, including the person whose work was dropped. They can push them back (git push origin <hash>:main, with care), and GitHub/GitLab can often help via their branch activity or audit logs.

    Deleting and pruning branches, pushing tags

    Deleting a local branch does not delete it on the server, and a branch deleted on the server lingers as origin/branch in your clone until you prune.

    Tags are not pushed by default

    A plain git push sends branches only. Tags have to be pushed explicitly:

    $ git tag -a v1.5.0 -m "Release 1.5.0"
$ git push origin v1.5.0

$ git push --tags
# delete a tag on the remote

    Authentication: HTTPS vs SSH

    The remote URL decides how you authenticate. https://github.com/acme/widget.git uses HTTPS. git@github.com:acme/widget.git uses SSH. Both are fine. You can switch any time with git remote set-url.

    HTTPS

    Works through almost any firewall or proxy. Authenticates with a token, usually managed for you.

    • GitHub no longer accepts your account password for Git operations (since 2021).
    • Git Credential Manager (bundled with Git for Windows, available for macOS and Linux) opens a browser sign-in once and stores the token securely.
    • Alternatively create a personal access token (fine-grained, with an expiry and only the repos you need) and paste it when asked for a password.

    SSH

    Uses a key pair: the private key stays on your machine, the public key goes to your account.

    • No tokens to rotate. Protect the key with a passphrase plus ssh-agent.
    • One key can serve GitHub, GitLab and your own servers.
    • Port 22 is blocked on some networks. GitHub also offers SSH over port 443 (ssh.github.com).

    HTTPS with a credential manager

    $ git config --global credential.helper
manager
# macOS keychain alternative
$ git config --global credential.helper osxkeychain
# first push opens a browser window to sign in; later pushes are silent
$ git push
    Do not put tokens in URLs

    Avoid remote URLs like https://user:ghp_xxx@github.com/.... The token ends up in plain text in .git/config, shell history and CI logs. Let a credential helper store it instead.

    The pull-request workflow

    On GitHub, Bitbucket and Gitea it is called a pull request. GitLab calls it a merge request. Either way it is a proposal to merge one branch into another, wrapped in a page for review, discussion and automated checks. Git itself knows nothing about PRs. They are built on the branch and push mechanics you already know.

    1. Start from an up-to-date main

      git switch main then git pull --ff-only. Starting from stale code is the most common source of avoidable conflicts.

    2. Create a focused branch

      git switch -c fix/currency-rounding. One topic per branch keeps reviews small and fast.

    3. Commit in small, meaningful steps

      Clear messages help reviewers follow your reasoning. Run tests locally before pushing.

    4. Push and set the upstream

      git push -u origin fix/currency-rounding. The server prints a link to open a PR.

    5. Open the pull request

      Use the link, the web UI, or the CLI (gh pr create for GitHub, glab mr create for GitLab). Pick the base branch (usually main), describe what and why, link the issue, and request reviewers. Open it as a draft if it is not ready.

    6. Address review feedback

      Just commit and git push again. The PR updates automatically. CI runs on every push.

    7. Keep it current with main

      If main moved and conflicts appear, either git fetch + git rebase origin/main + git push --force-with-lease, or git merge origin/main + git push. Follow your team's convention.

    8. Merge

      Once approved and green, merge in the web UI with the team's chosen method: Create a merge commit (--no-ff), Squash and merge (one commit), or Rebase and merge (linear, commits re-created).

    9. Clean up

      Delete the remote branch (usually a button), then locally: git switch main, git pull, git branch -d fix/currency-rounding (use -D after a squash or rebase merge, since Git cannot see those as merged), and git fetch --prune.

    Forks and keeping a fork in sync

    When you cannot push to a project (typical in open source), you fork it: the hosting site makes a server-side copy under your account. You clone your fork (so origin is the fork, which you can push to) and add the original project as a second remote, conventionally named upstream, which you only fetch from.

    # one-time setup (after clicking "Fork" on GitHub)
$ git clone git@github.com:you/widget.git
$ cd widget
$ git remote add upstream https://github.com/acme/widget.git
$ git remote -v
origin    git@github.com:you/widget.git (fetch)
origin    git@github.com:you/widget.git (push)
upstream  https://github.com/acme/widget.git (fetch)
upstream  https://github.com/acme/widget.git (push)
# optional: make accidental pushes to upstream impossible
$ git remote set-url --push upstream DISABLED

    Syncing your fork with upstream

    Your fork does not update itself. Whenever upstream moves, bring its main into your local main, then push it to your fork:

    $ git fetch upstream

   c3b2a1f..71e0d9a  main       -> upstream/main
$ git switch main
$ git merge --ff-only upstream/main
Updating c3b2a1f..71e0d9a

   c3b2a1f..71e0d9a  main -> main
# start new work from the fresh upstream main
$ git switch -c fix/typo-in-install upstream/main
    Keep your fork's main pristine

    Never commit directly to main in a fork. Always use topic branches. Then syncing is always a clean fast-forward. If --ff-only fails, you committed to main by mistake: move those commits to a branch and reset main to upstream/main. GitHub's Sync fork button and gh repo sync do the same fast-forward on the server side.

    To update an open PR branch with upstream changes: git fetch upstream, git rebase upstream/main on your branch, then git push --force-with-lease origin <branch>. The PR, which lives on upstream but reads from your fork's branch, updates automatically.

    Check yourself

    What is the difference between git fetch and git pull?

    git fetch downloads new commits and updates remote-tracking branches like origin/main, but never changes your local branches or files. git pull runs a fetch and then integrates the upstream branch into your current branch by merging (default) or rebasing (--rebase or pull.rebase true). Fetch is always safe. Pull can create merge commits or stop on conflicts.

    git status says "Your branch is up to date with 'origin/main'", yet a teammate says they pushed an hour ago. Who is right?

    Probably both. git status compares with your local origin/main, which only changes when you fetch, pull or push. Run git fetch and check again: you will likely be "behind 1".

    Your push is rejected with "(fetch first)". What happened, and what should you do?

    Someone pushed to the branch after your last fetch, so your push would not be a fast-forward and the server refuses to discard their commits. Integrate their work with git pull --rebase (or a merge), resolve any conflicts, test, and push again. Do not reach for --force: that would delete their commits from the branch.

    Why prefer --force-with-lease over --force after rebasing your feature branch?

    --force-with-lease only overwrites the remote branch if it still points where your origin/<branch> says it does. If someone else pushed in the meantime, the push fails with "stale info" instead of silently throwing away their commits. --force overwrites unconditionally.

    Has the commit been pushed to a branch other people use? If no, you can rewrite freely: amend, reset, rebase. If yes, add new commits on top instead (git revert). Rewriting shared history forces everyone else to untangle their copies.

    Discarding and unstaging with git restore

    git restore (Git 2.23+) copies file content backwards through the three areas. It never moves a branch and never creates commits. It only overwrites files.

    git restore <file> and git checkout -- <file> overwrite uncommitted edits. Git never stored them, so the reflog cannot bring them back. If you are unsure, git stash first. Stashing is reversible.

    Fixing the last commit with --amend

    git commit --amend takes whatever is staged now and makes a new commit that replaces the tip of the branch. Commits cannot be edited, so you get a brand-new one with a new hash. The old commit is simply abandoned.

    # 1. Just fix the message
$ git commit --amend -m "Add login form validation"
[main b5e0f19] Add login form validation

# 2. Add a file you forgot, keep the message as-is
$ git add src/validators.js

[main c81a2d4] Add login form validation
 Date: Tue Oct 13 10:42:07 2026 +0200

    Already pushed?

    Amending a pushed commit means your local branch and the remote now disagree. A normal git push is rejected, and forcing it rewrites history for everyone who pulled. On your own feature branch that is fine: use git push --force-with-lease. On main or any shared branch, make a new commit instead.

    git reset: moving the branch pointer

    git reset <commit> does one thing first: it moves the current branch (and therefore HEAD) to <commit>. The mode then decides how much further the reset spreads: into the staging area, and then into your working tree.

    --soft. Squash or redo commits

    Made five tiny "wip" commits? git reset --soft HEAD~5 then a single git commit squashes them into one.

    --mixed. Re-split a commit

    Undo the commit, keep the edits, then stage and commit them in smaller logical pieces with git add -p.

    --hard. Start over

    Abandon local commits and edits. Classic use: git reset --hard origin/main to match the remote exactly.

    Reset with a path is something else

    When you give git reset a file path, it cannot move a branch "for one file". Instead it only copies that file from the commit into the staging area. git reset app.js = git reset HEAD app.js = git restore --staged app.js. That is why the old tutorials used it to unstage.

    Undo a reset

    Every reset records the previous tip in ORIG_HEAD. Right after a mistaken reset, git reset --hard ORIG_HEAD puts things back (for commits). For older mistakes, use the reflog (below).

    What --hard really destroys

    Commits you reset away are recoverable for weeks via the reflog. Uncommitted changes in tracked files are not: --hard overwrites them with no backup. Run git status first, and stash anything you want to keep. (git reset --keep <commit> is a safer alternative: it refuses to run if it would overwrite local edits.)

    git revert: undoing by adding a commit

    git revert <sha> computes the inverse of that commit's diff (added lines become removed and vice versa) and records it as a new commit. History only grows, so everyone who already pulled just pulls the revert like any other commit. This is the right tool for pushed, shared branches.

    $ git log --oneline -4
e4b8d02 (HEAD -> main, origin/main) Add password reset email
7d21c4e Add caching layer
3c9e2a1 Add login form
a1f3b07 Initial commit

$ git revert 7d21c4e --no-edit
[main 5b1f0a9] Revert "Add caching layer"
 2 files changed, 3 insertions(+), 41 deletions(-)
 delete mode 100644 src/cache.js

$ git push
# no force needed: history only moved forward

    Without --no-edit, Git opens an editor with a message like Revert "Add caching layer" followed by This reverts commit 7d21c4e…. Use the body to explain why.

    Options worth knowing

    • git revert HEAD: revert the most recent commit.
    • git revert HEAD~3..HEAD: revert the last three commits, one revert commit each (newest first).
    • git revert -n <a> <b> (--no-commit): apply the inverses to the index without committing, so you can combine them into one commit.
    • If a revert conflicts (later commits touched the same lines), fix the files, git add them, then git revert --continue, or bail out with git revert --abort.

    Reverting a merge commit

    A merge has two parents, so "the inverse of its changes" is ambiguous: changes relative to which parent? You must pick the mainline with -m. Parent 1 is the branch you were on when you merged (usually main), so -m 1 means "undo everything the merged branch brought in".

    $ git revert 9c1e4f2
error: commit 9c1e4f2 is a merge but no -m option was given.
fatal: revert failed

$ git revert -m 1 9c1e4f2
[main 0d7a3e5] Revert "Merge branch 'feature/search'"
 4 files changed, 12 insertions(+), 188 deletions(-)
    The merge-revert trap

    After reverting a merge, Git still considers the feature's commits merged. If you fix the feature and merge it again, only the new fix commits come in. The original work stays reverted. To bring it all back, first revert the revert (git revert 0d7a3e5), then merge the fixes.

    Reset or revert?

    git reset

    Moves the branch pointer backwards. The commits disappear from the branch.

    • Rewrites history: the commits drop off the branch (still in the reflog for a while)
    • Needs --force-with-lease to push if already pushed
    • Clean history, as if the mistake never happened
    • Use for local, unpushed work and your own feature branches

    git revert

    Adds a commit that cancels an earlier one. The mistake remains visible.

    • Never rewrites history
    • Pushes normally, collaborators just pull
    • Can undo an old commit while keeping everything after it
    • Use for shared branches: main, release branches, anything deployed

    git reflog: your safety net

    Every time HEAD moves (commit, checkout, switch, reset, rebase, merge, amend, pull), Git appends a line to a private, local log: the reflog. Commits that no branch points to anymore are still in the object database, and the reflog tells you their hashes. That is why "I lost my commits" is almost always fixable.

    # Oops: threw away two commits
$ git reset --hard HEAD~2
HEAD is now at 3c9e2a1 Add login form

$ git reflog
3c9e2a1 (HEAD -> main) HEAD@{0}: reset: moving to HEAD~2

7d21c4e HEAD@{2}: commit: Add caching layer
3c9e2a1 (HEAD -> main) HEAD@{3}: checkout: moving from experiment to main

9f2c6d8 HEAD@{5}: commit: Try LRU eviction

    Rescue first, think later

    When you find a lost commit, pin it with a branch immediately: git branch rescue <sha>. Now it is safe from garbage collection and you can inspect, cherry-pick or merge it calmly.

    How long?
    Reflog entries expire after 90 days by default (gc.reflogExpire). Entries for commits no longer reachable from any branch expire after 30 days (gc.reflogExpireUnreachable). After that, git gc may delete the objects.
    Local only
    The reflog is never pushed or cloned. A fresh clone has an empty reflog. Your teammate's reflog cannot help you, and yours cannot help them.
    Per-branch reflogs
    git reflog show main lists how main itself moved, and main@{2} refers to it. Deleting a branch deletes its own reflog, which is why you search the HEAD reflog instead.
    Never-committed work
    The reflog only tracks commits. Content you once staged but never committed exists as a dangling blob: git fsck --lost-found writes those to .git/lost-found/ as a last resort.

    Stashing work in progress

    An urgent bug lands while you are halfway through a feature. git stash takes your uncommitted changes (staged and unstaged), saves them as special commits on a stack, and resets your working tree to HEAD. Later you re-apply them, on the same branch or a different one.

    apply vs pop

    git stash apply

    Re-applies the stash and keeps it on the stack. Good when you want to apply the same changes to several branches, or are not sure it will apply cleanly.

    git stash pop

    Re-applies and then drops it. If the apply hits a conflict, Git does not drop the entry: resolve the conflict, then git stash drop yourself.

    Stashes are not a filing cabinet

    Stashes are easy to forget and easy to lose with drop or clear. For anything you will need beyond today, commit it on a branch (git switch -c wip/login && git commit -am "WIP").     Cleaning untracked files with git clean

    git clean deletes files that Git is not tracking: build output, logs, stray experiments. Because Git never stored these files, there is no reflog, no stash, nothing to recover from. Always preview first.

    Check yourself

    You committed with the wrong message and have not pushed. What is the fastest fix, and why does the commit hash change?

    git commit --amend -m "Correct message". Commits are immutable: the message is part of the data that gets hashed, so Git creates a new commit with a new hash and moves the branch to it. The old commit is abandoned (but still in the reflog).

    What is the difference between git reset --soft HEAD~1, git reset HEAD~1 and git reset --hard HEAD~1?

    All three move the branch back one commit. --soft leaves the index and files alone, so the changes appear staged. The default --mixed also resets the index, so the changes appear as unstaged edits. --hard also overwrites the working tree, so the changes vanish (the commit is recoverable via the reflog, uncommitted edits are not).

    A bad commit was pushed to main three days ago and five teammates have pulled since. How do you undo it?

    git revert <sha> and push. It adds an inverse commit without rewriting history, so nobody has to repair their clone. Resetting and force-pushing would break everyone's local main.

    You ran git reset --hard HEAD~3 by mistake. How do you get the commits back?

    Immediately: git reset --hard ORIG_HEAD. Later: run git reflog, find the entry just before reset: moving to HEAD~3 (e.g. HEAD@{1}), and git reset --hard HEAD@{1}, or pin it with git branch rescue HEAD@{1}. Uncommitted edits that the reset overwrote cannot be recovered this way.

    Naming commits: revision syntax

    Anywhere Git wants a commit you can write more than a hash. These expressions work with log, show, diff, reset, switch, rebase and the rest.

    ExpressionMeans
    HEAD or @The commit you have checked out.
    HEAD~, HEAD~1Its first parent.
    HEAD~3Three generations back, always via first parents (= HEAD^^^).
    HEAD^, HEAD^1First parent (same as HEAD~).
    HEAD^2Second parent. Only exists on merge commits. ^ picks which parent, ~ picks how far.
    main@{yesterday}, main@{2.weeks.ago}Where your local main pointed at that time, from the reflog. Not where it was on the server.
    main@{1}, HEAD@{3}The previous value of the ref / HEAD three moves ago (reflog).
    @{u}, main@{upstream}The upstream branch (e.g. origin/main). git log @{u}.. = what you'd push.
    @{-1}The branch you were on before (what git switch - uses).
    :/fix loginYoungest commit whose message matches the regex "fix login".
    v1.2.0^{commit}Peel an (annotated) tag to the commit it points at.

    Ranges are set operations on "commits reachable from X". They are the key to questions like "what is on my branch that is not on main?". Picture main and feature diverging from a common merge base:

    git bisect: binary search for the bug

    Something worked in v2.3.0 and is broken now, with 200 commits in between. You do not need to read them. git bisect checks out the midpoint, you say "good" or "bad", and it halves the range each time. 200 commits take about 8 tests. 1,000 take about 10.

    1. Start and mark the endpoints

      Tell Git a commit where the bug exists (usually HEAD) and one where it did not (a tag, an old commit).

    2. Test what Git checks out

      Git puts you in detached HEAD at the midpoint. Build, run the test, try the feature.

    3. Answer good or bad

      git bisect good or git bisect bad. If this commit cannot be tested (does not build for unrelated reasons), git bisect skip.

    4. Repeat until Git names the culprit

      Git prints "<sha> is the first bad commit" with its details.

    5. Reset

      git bisect reset returns you to the branch you started on. Do not forget this step.

    $ git bisect start

$ git bisect bad
status: waiting for good commit(s), bad commit known
$ git bisect good v2.3.0

    Check yourself

    HEAD is a merge commit. What is the difference between HEAD~2 and HEAD^2?

    HEAD~2 is the grandparent along first parents: two steps back on the branch you merged into. HEAD^2 is the merge's second parent: the tip of the branch that was merged in. ~ counts generations, ^n selects a parent.

    Your PR shows 40 changed files, but the reviewer's view shows 6. You ran git diff main..feature. What happened?

    Two-dot git diff compares the two tips directly, so everything that landed on main after you branched appears too (in reverse). Pull requests use three dots: git diff main...feature compares the merge base with feature, showing only your branch's changes.

    A function called validateIban() no longer exists anywhere in the code. How do you find out when and why it was removed?

    git log -S "validateIban" --oneline lists the commits that added or removed that string. The newest is usually the removal. git show <sha> shows the diff and message explaining why, and git show <sha>^:path/to/file gives you the file as it was just before. Blame cannot help: it only annotates lines that still exist.

    With git bisect run, what exit code should your script return when a commit does not compile for an unrelated reason?

    125, which means "skip". Git then tests a nearby commit instead. Returning 1 would wrongly mark it bad and could make bisect blame the wrong commit. 0 marks it good.

    Interactive rebase: edit history before you share it

    A normal rebase replays your commits onto a new base. An interactive rebase stops first and hands you a to-do list: one line per commit, oldest at the top. You edit that list to reorder, merge, rename, split or delete commits, save, and Git executes the plan line by line. It is the single best tool for turning "wip", "fix typo", "actually fix it" into a reviewable series of commits.

    Say your feature/login branch has four commits you have not pushed yet:

    $ git log --oneline -5
5d2b7f3 (HEAD -> feature/login) Add debug logging
c41e9a0 Add client-side validation
8b7d4e1 Fix typo in login form
3f9a1c2 Add login form markup
1a2b3c4 (main) Set up project skeleton
$ git rebase -i HEAD~4

    HEAD~4 means "the commit four steps back". Everything after it goes into the list. Git opens your editor with this file:

    pick 3f9a1c2 Add login form markup
pick 8b7d4e1 Fix typo in login form
pick c41e9a0 Add client-side validation
pick 5d2b7f3 Add debug logging

# Commands:
# p, pick <commit> = use commit
# r, reword <commit> = use commit, but edit the commit message
# e, edit <commit> = use commit, but stop for amending
# s, squash <commit> = use commit, but meld into previous commit
# f, fixup [-C | -c] <commit> = like "squash" but keep only the previous
#                    commit's log message, unless -C is used, in which case
#                    keep only this commit's message; -c is same as -C but
#                    opens the editor
# x, exec <command> = run command (the rest of the line) using shell
# b, break = stop here (continue rebase later with 'git rebase --continue')
# d, drop <commit> = remove commit
# l, label <label> = label current HEAD with a name
# t, reset <label> = reset HEAD to a label
# m, merge [-C <commit> | -c <commit>] <label> [# <oneline>]
# u, update-ref <ref> = track a placeholder for the <ref> to be updated

# These lines can be re-ordered; they are executed from top to bottom.
#
# If you remove a line here THAT COMMIT WILL BE LOST.
#
# However, if you remove everything, the rebase will be aborted.

    You decide the typo fix belongs inside the markup commit, validation should be folded in too (with a combined message), the debug logging should disappear, and the tests should run once the history is rewritten. Edit the list to:

    rewordReplay it, then open the editor for a new message.Fixing "wip" or a vague message.

    Mark the commit edit. When the rebase stops on it, undo the commit but keep its changes, then commit in smaller pieces:

    Only rewrite what you have not shared

    Every rewritten commit gets a new hash. If teammates already built on the old commits, your rewritten branch will diverge from theirs and you will need git push --force-with-lease, which forces everyone else to recover. Tidy your history before pushing, or on a branch only you use.

    Undo a botched rebase

    The old commits are not deleted. git reflog shows an entry like 5d2b7f3 HEAD@{6}: rebase (start): checkout HEAD~4. After a finished rebase, ORIG_HEAD also points to the pre-rebase tip, so git reset --hard ORIG_HEAD rewinds the whole thing.

    Fixup commits and --autosquash

    Reordering lines by hand gets tedious. Instead, tell Git at commit time which earlier commit a fix belongs to. git commit --fixup=<commit> creates a commit whose message is fixup! <original subject>. Later, --autosquash moves every such commit under its target and marks it fixup for you.

    Back on the original four-commit branch, suppose code review finds a bug in 3f9a1c2:

    # stage the fix, then point it at the commit it belongs to
$ git add src/login.html
$ git commit --fixup=3f9a1c2
[feature/login 9d4e2aa] fixup! Add login form markup
 1 file changed, 1 insertion(+), 1 deletion(-)
$ git rebase -i --autosquash main

    The to-do list arrives already arranged. You only need to save:

    pick 3f9a1c2 Add login form markup
fixup 9d4e2aa fixup! Add login form markup
pick 8b7d4e1 Fix typo in login form
pick c41e9a0 Add client-side validation
pick 5d2b7f3 Add debug logging
    • git commit --squash=<commit> works the same way but becomes a squash line, letting you edit the combined message.
    • git commit --fixup=amend:<commit> also replaces the target's message. --fixup=reword:<commit> changes only the message.
    • git config --global rebase.autoSquash true makes every git rebase -i autosquash. Since Git 2.44, --autosquash also works without -i.
    Review-friendly workflow

    During code review, push fixup! commits so reviewers can see exactly what changed since their last look. Right before merging, run git rebase -i --autosquash main and force-push with lease once. Reviewers get small diffs. main gets a clean history.

    A cherry-picked commit is a duplicate with a different hash.     Tags: names for releases

    A branch is a pointer that moves with every commit. A tag is a pointer that is meant to stay put forever, usually marking a release. There are two kinds:

    Lightweight tag

    Just a ref file, refs/tags/v1.1.0, containing a commit hash. No author, no date, no message.

    • git tag v1.1.0
    • Fine for private bookmarks ("before-refactor").
    • Ignored by git describe unless you pass --tags.

    Annotated tag

    A real object in the database with tagger, date, message and an optional signature. The ref points to that tag object, which points to the commit.

    • git tag -a v1.2.0 -m "Release 1.2.0"
    • Use these for every release.
    • Pushed by git push --follow-tags.
    $ git tag -a v1.2.0 -m "Release 1.2.0: SSO login, faster invoice export"

    git push does not send tags by default. Push them explicitly:

    $ git push origin v1.2.0            # one tag

    Never move a published release tag

    Other clones will not pick up a changed tag (fetch will not overwrite an existing tag without --force), so two people can have different "v1.2.0"s. If a release is broken, ship v1.2.1.

    Semantic versioning

    Most projects tag as vMAJOR.MINOR.PATCH: bump MAJOR for breaking changes, MINOR for backwards-compatible features, PATCH for bug fixes. Pre-releases look like v2.0.0-rc.1. Sorting with --sort=v:refname understands these numbers, so v1.10.0 comes after v1.9.0.

    git describe: a human-readable build version

    $ git describe
v1.2.0-14-g7d3e1a9
$ git describe --tags --dirty
v1.2.0-14-g7d3e1a9-dirty

    Read it as: nearest annotated tag v1.2.0, then 14 commits on top, then g + abbreviated hash. -dirty appears when there are uncommitted changes. Build scripts embed this string so every binary knows exactly which commit it came from.

    Worktrees: several branches checked out at once

    You are halfway through a feature when production breaks. The stash-switch-fix-switch-pop dance works, but it throws away your editor state, triggers full rebuilds, and fails if you also want to keep a long test run going. A worktree is a second (or third) working directory attached to the same repository, each with its own branch checked out.

    Stash and switch

    • One directory. You must park unfinished work.
    • Switching rewrites files, so editors and build caches churn.
    • Easy to forget a stash for weeks.

    Worktree

    • Unfinished work stays exactly where it is.
    • Run tests in one tree while coding in another.
    • No second clone: objects are shared, so it is fast and cheap on disk.
    One branch, one worktree

    Git refuses to check out a branch that is already checked out elsewhere, because two working trees moving the same branch would trample each other: fatal: 'main' is already used by worktree at '/home/ada/code/shop'. Use git worktree add --detach ../tmp main if you only need a read-only look.

    Submodule pitfalls
    • Detached HEAD inside the submodule. update checks out a commit, not a branch. Run git switch main inside it before making changes, or your commits will float.
    • Forgetting to commit the pointer. Committing inside the submodule does not update the parent. You must git add vendor/ui-kit and commit in the superproject too.
    • Pushing in the wrong order. If you push the parent before the submodule, teammates get a pointer to a commit that does not exist on the server. git push --recurse-submodules=check (or =on-demand) prevents this.
    • Stale checkouts after pull. git config --global submodule.recurse true makes pull, switch and friends update submodules automatically.

    The alternative: git subtree

    git subtree copies the other project's files directly into a subdirectory of your repository (optionally squashed into one commit). Clones need no extra steps and nobody has to learn submodule commands. The cost is a bigger repository and more manual work to send changes back upstream.

    $ git subtree add --prefix=vendor/ui-kit https://github.com/acme/ui-kit.git main --squash
$ git subtree pull --prefix=vendor/ui-kit https://github.com/acme/ui-kit.git main --squash

    Rule of thumb: use submodules when the dependency is developed independently and you pin exact versions. Use subtree (or a package manager) when you mostly consume it and want the simplest possible clone.

    undo uses --soft on purpose: it only moves the branch back and keeps your changes staged, so it can never destroy work. Avoid aliasing destructive commands such as reset --hard to short, easy-to-mistype names.

    Big files and huge repositories: LFS, partial clone, sparse-checkout

    Git keeps every version of every file forever, and every clone downloads all of it. That is perfect for source code and painful for 400 MB design files or monorepos with millions of files. Three tools address different parts of the problem.

    Git LFS

    Large binaries are replaced in history by tiny pointer files. The real content lives on an LFS server and is downloaded only for the commits you check out.

    Partial clone

    Download all commits and trees but fetch file contents (blobs) lazily, only when something needs them.

    Sparse-checkout

    Materialize only the directories you work on. The rest of the repository stays out of your working tree.

    Check yourself

    In an interactive rebase, what is the difference between squash and fixup?

    Both meld the commit into the one above it. squash opens the editor with both messages so you can write a combined one. fixup silently discards the folded commit's message and keeps the previous one. git commit --fixup=<sha> plus git rebase -i --autosquash automates the reordering.

    You cherry-picked commit 9e4b onto main. Why does the new commit have a different hash, and why add -x?

    A commit's hash covers its parent, tree, timestamps and message. The copy has a different parent (the tip of main), so it is a different commit even though the diff is the same. -x records "(cherry picked from commit 9e4b...)" in the message, so anyone can trace the copy back to the original.

    When is a worktree better than git stash, and what can you not do with worktrees?

    A worktree is better whenever you need two branches at the same time: a hotfix while a feature is half-done, reviewing a PR while tests run, or comparing builds side by side. Nothing is parked or rewritten, and objects are shared so it costs almost no disk. You cannot check out the same branch in two worktrees at once (use --detach for a read-only copy).

    You ran git tag v2.0.0 and git push. Why does nobody see the tag, and what would you do differently?

    git push does not send tags by default, and a lightweight tag would not be pushed by --follow-tags either. For a release, create an annotated tag with git tag -a v2.0.0 -m "Release 2.0.0", then push it with git push origin v2.0.0 or git push --follow-tags.

    08Inside Git

    Git stores four kinds of objects and a few text files that point at them. That store explains branches, rebase, and the reflog.

    A tour of the .git directory

    Everything Git knows about your project lives in the hidden .git folder at the repository root. Your files outside it are just one checked-out view. Delete the working tree and you lose nothing that was committed. Delete .git and the history is gone.

    $ ls -F .git
COMMIT_EDITMSG  HEAD       ORIG_HEAD  description  index  logs/     packed-refs
FETCH_HEAD      config     hooks/     info/        objects/  refs/
$ cat .git/HEAD

    HEAD
    A one-line text file saying what is checked out. Normally ref: refs/heads/main (a pointer to a branch). In detached state, a raw commit hash.
    config
    Repository-level settings in INI format: remotes, branch upstreams, and any git config you ran without --global. It overrides ~/.gitconfig.
    refs/
    Named pointers to commits: refs/heads/ (local branches), refs/remotes/origin/ (remote-tracking branches), refs/tags/, plus refs/stash. Each is a tiny file holding a 40-character hash.
    objects/
    The database itself: every blob, tree, commit and tag, either as individual compressed files in two-character subfolders (objects/3b/18e5...) or bundled in objects/pack/.
    index
    The staging area: a binary file listing every path that will go into the next commit, with its blob hash, mode and file-system stat data.
    logs/
    The reflogs: an append-only history of where HEAD and each branch pointed, and why. This is what git reflog reads.
    hooks/
    Scripts Git runs at specific moments (pre-commit, pre-push, ...). New repositories contain only *.sample files, which do nothing.
    packed-refs
    Many refs (especially tags and remote branches) packed into one text file for speed. Loose files in refs/ take precedence.
    ORIG_HEAD, FETCH_HEAD, MERGE_HEAD
    Temporary pointers: where HEAD was before a risky operation (reset, rebase, merge), what was just fetched, and what is being merged.
    info/exclude
    A private .gitignore for this clone only. Never committed.
    Look, but do not edit by hand

    Reading these files is safe and instructive. Editing them directly is almost never needed: every one has a command (git config, git update-ref, git symbolic-ref) that does the same thing with locking and logging.

    The four object types

    The objects/ database stores exactly four kinds of things. Each object is immutable and is named by the hash of its own content.

    blob. File contents

    The raw bytes of one file version. No filename, no permissions, no date. Two files with identical bytes are the same blob.

    tree. A directory

    A sorted list of entries: mode, type, hash and name. Entries point to blobs (files) or other trees (subdirectories).

    commit. A snapshot + story

    Points to one root tree and zero or more parent commits, and records author, committer, timestamps and message.

    tag. Annotated tag

    Points to another object (usually a commit) and adds a tag name, tagger, date, message and optional signature.

    Notice what a commit is not: it is not a diff. It is a complete snapshot, made cheap by sharing. When git show displays a diff, Git computes it on the fly by comparing the commit's tree with its parent's tree. And because trees are hashed too, Git can skip whole unchanged directories instantly: if src/ has the same tree hash in two commits, nothing inside it changed.

    Content addressing: the name is the hash

    An object's name is the SHA-1 hash of a short header (type, a space, the size in bytes, a NUL byte) followed by the content. You can reproduce Git's hash without Git:

    $ printf 'blob 12\0hello world\n' | sha1sum
3b18e512dba79e4c8300dd08aeb37f8e728b8dad  -
$ echo 'hello world' | git hash-object --stdin
3b18e512dba79e4c8300dd08aeb37f8e728b8dad

    Every Git user on the planet who stores the line "hello world" gets that exact hash. The consequences are profound:

    • Deduplication for free. Identical content is stored once, no matter how many files, directories or commits contain it.
    • Integrity. If a single bit of an object changes on disk, its hash no longer matches its name, and git fsck notices.
    • Chained trust. A commit hash covers its tree hash, which covers every blob hash, and its parent hash, which covers the entire history. One 40-character id pins down the whole project state.
    • Immutability. You cannot "edit" an object. Changed content means a different name. Every history-rewriting command really creates new objects.
    SHA-1, SHA-256 and safety

    SHA-1 is no longer considered collision-resistant (a practical collision was published in 2017). Since 2.13, Git uses a hardened SHA-1 implementation that detects the known collision attack and refuses such objects. Git also supports SHA-256 repositories (git init --object-format=sha256), with 64-character ids, and the project has announced that Git 3.0 will make SHA-256 the default for new repositories. Interoperability with SHA-1 repositories and hosting sites is still the sticking point, so most repositories today remain SHA-1.

    A branch is not a container of commits. It is a 41-byte file: a commit hash and a newline. That is the whole implementation.

    Git 2.45 added an alternative ref storage format, reftable (git init --ref-format=reftable), which keeps all refs in compact binary tables instead of one file per ref.     What the model explains

    With objects and refs in mind, revisit some everyday behaviors:

    Branches are cheap

    Creating a branch writes one 41-byte file. No files are copied, no history is duplicated. Switching branches rewrites only files whose blob hashes differ between the two trees.

    Rebase makes new commits

    A commit's hash covers its parent. Moving a commit onto a new base changes the parent, so it must be a new object with a new hash. The originals stay in the database.

    The reflog can rescue you

    Every time a ref moves, Git appends the old and new hash to .git/logs/. Old commits are still in objects/, so pointing a branch back at them restores everything.

    $ git reflog show feature -3
0be4c71 feature@{0}: rebase (finish): refs/heads/feature onto e91c5d2b0a7f3e8c1d6b9a4f2e0c7d5b3a1f9e8c
8b7d4e1 feature@{1}: commit: Add client-side validation
3f9a1c2 feature@{2}: commit: Add login form markup
# regret the rebase? point the branch back at the old commits
$ git reset --hard feature@{1}
HEAD is now at 8b7d4e1 Add client-side validation
    Same idea, everywhere

    commit --amend, cherry-pick, rebase and filter-repo all follow the same pattern: write new objects, move a ref. reset only moves a ref. merge writes one new commit with two parents. Nothing in Git ever modifies an existing object.

    Unreachable objects, dangling commits and git fsck

    An object is reachable if you can get to it by starting from any ref (branches, tags, remote-tracking branches, the stash, and reflog entries) and following parent and tree pointers. Everything else is unreachable. A dangling object is an unreachable one that nothing else points to either: the tip of a lost chain.

    Check yourself

    You copy logo.png into five directories and commit. How many new blobs does Git store?

    One. A blob's name is the hash of its content alone, so all five paths point to the same object. The filenames live in tree entries, which is why each of the five directories gets its own (new) tree, but the image bytes are stored once.

    What does .git/HEAD contain normally, and what changes when HEAD is detached?

    Normally it is a symbolic ref: the text ref: refs/heads/main, so commits advance the main branch file. When detached, it contains a raw commit hash, so new commits are referenced only by HEAD (and the reflog) until you create a branch with git switch -c <name>.

    Why cannot Git rebase a commit "in place" while keeping its hash?

    The hash is computed over the commit's full content, which includes the parent hash and the tree hash. Changing the base changes the parent (and usually the tree), so the result is a different object with a different name. The old commit still exists unchanged, which is exactly why git reflog and ORIG_HEAD can bring it back.

    You staged a file during a merge conflict. What happened in the index, in terms of stage numbers?

    During the conflict the index held up to three entries for the path: stage 1 (common ancestor), stage 2 (ours) and stage 3 (theirs). git add replaced them with a single stage-0 entry pointing to the blob of your resolved file, which is what tells Git the conflict is resolved and lets write-tree succeed.

    Writing great commit messages

    A commit message is a note to a future developer, often you in eight months, reading git log or git blame to find out why a line looks the way it does. The diff already shows what changed. The message has to explain why, because nothing else will.

    Short subject line

    Keep the first line to about 50 characters (72 at most). It appears in --oneline, PR titles, GitHub's UI and email subjects, and gets cut off when it runs long.

    Wrap the body

    Leave a blank line after the subject, then wrap body text at 72 columns so it reads cleanly in an 80-column terminal, where git log indents it by 4.

    Imperative mood

    Write "Add retry to upload", not "Added" or "Adds". A good subject finishes the sentence "If applied, this commit will...". Git's own messages do this too ("Merge branch...", "Revert...").

    Why over what

    Explain the problem, the reasoning, and any trade-off or alternative you rejected. Link the issue. Skip the line-by-line narration, since the diff already shows that.

    Bad

    • fix
    • WIP
    • updated stuff in login and also refactored utils and fixed the tests
    • Changed timeout from 5000 to 15000
    • addressed review comments

    These say nothing, mix unrelated changes, or repeat the diff without giving a reason. Nobody can find them in a search six months later.

    • Fix crash when cart contains a deleted product
    • Raise upload timeout to fit 50 MB files on 3G
    • Extract date parsing into utils/dates.js

    • Validate email before sending magic link

    Branching strategies

    A branching strategy is a team agreement on where work happens, how long branches live, and how code gets to production. Git enforces none of it. The three below are the ones you will run into.

    GitHub flow

    This is the simplest model, and it suits most web apps that deploy continuously. main is always deployable. All work happens on a short-lived, descriptively named branch, which goes through a pull request (CI plus review), is merged, and is deployed right away.

    $ git switch main && git pull
$ git switch -c feature/login
# ...work, commit, repeat...
$ git push -u origin feature/login
$ gh pr create --fill
Creating pull request for feature/login into main in acme/shop

https://github.com/acme/shop/pull/517

    Trunk-based development

    Trunk-based development pushes GitHub flow further. Everyone integrates into main (the "trunk") at least daily. Branches, if used at all, live for hours rather than weeks. Unfinished features are merged anyway and stay hidden behind feature flags, which are runtime switches that turn code paths on per environment, per user, or for a percentage of traffic.

    Why teams like it

    Integration pain grows with how far branches drift apart. Merging small changes every day means conflicts are small and found early, and CI tests the code that will ship. The cost is discipline: you need fast, reliable CI, good test coverage, and a habit of cleaning up feature flags once a feature is fully rolled out.

    Git Flow

    Git Flow, from Vincent Driessen's 2010 post, uses two permanent branches: main holds only released versions, and develop is where integration happens. Three kinds of temporary branches sit around them:

    • feature/* branches come off develop and merge back into it.
    • release/* branches come off develop to stabilize a version, then merge into both main (tagged) and develop.
    • hotfix/* branches come off main for urgent production fixes, then merge into both main and develop.
    Why many teams moved away from Git Flow
    • It was designed for software shipped in numbered versions (desktop apps, firmware, libraries with several supported versions). For a web app deployed many times a day, the develop/release split is ceremony with no payoff.
    • Long-lived feature branches drift away from develop and lead to large, painful merges.
    • Every hotfix and release has to merge into two branches, and forgetting one causes a regression.
    • In 2020 the original author added a note to his post recommending simpler workflows such as GitHub flow for continuously delivered software.

    Git Flow still fits if you really do maintain several released versions at once. Otherwise start with GitHub flow and move toward trunk-based development as your CI matures.

    Pull request etiquette

    A pull request asks a colleague to spend their attention on your work. Make it easy for them, and review their PRs the way you would like yours reviewed.

    1. Keep it small

      Review quality drops sharply past roughly 400 changed lines. Split big work into a stack of PRs: refactor first, then the feature, then cleanup. Move generated files and mass renames into their own PR.

    2. Write a real description

      Cover what changed and why, how you tested it, screenshots for UI changes, and anything risky or deliberately left out. Link the issue (Closes #482 closes it automatically on merge).

    3. Review your own diff first

      Read the PR in the web UI before you request reviewers. You will find stray debug logs, commented-out code and unrelated formatting changes every time.

    4. Use draft PRs early

      Open a draft (gh pr create --draft) to run CI and get early feedback on the approach before you polish. Mark it "Ready for review" when it is ready.

    5. Respond to every comment

      Fix it, or explain why not. Resolve threads once they are handled. During review, push new commits (or --fixup commits) instead of force-pushing, so reviewers can see what changed since their last look.

    As a reviewer, do

    • Review within a working day. Slow reviews are the biggest drag on a team.
    • Separate blocking issues from nits: "nit:", "optional:", "question:".
    • Explain why, and suggest concrete code (GitHub's "suggestion" blocks).
    • Comment on the code, not the person: "this could race" rather than "you forgot".
    • Approve with minor comments when you trust the author to address them.

    As a reviewer, avoid

    • Bikeshedding style that a formatter or linter should enforce.
    • Requesting a rewrite in your personal style when theirs is fine.
    • Rubber-stamping a 2,000-line PR with "LGTM" after skimming it.
    • Leaving the author waiting in silence after a round of changes.
    • Scope creep: "while you are here, could you also..." belongs in a new issue.

    If you committed a secret anyway

    Rotate first, clean up second

    The moment a secret is pushed, treat it as compromised. Revoke or rotate the key at the provider before you touch Git history.       It is easy: if the secret is only in your latest local commit, remove it and run git commit --amend. If it is further back, use git rebase -i to edit that commit. No force-push is needed because nobody else has it.

    10When something breaks

    Find your problem. Read what Git did. Then apply the fix. Stop before you type a command that deletes work.

    First aid: before you try anything

    Committed work is very hard to lose in Git. A commit is only garbage-collected once nothing refers to it any more, and the reflog keeps referring to old positions for a while (by default 90 days, or 30 days for commits no branch can reach). Uncommitted work is the fragile part. Before attempting any rescue, take these three cheap precautions:

    # 1. Understand where you are
$ git status
$ git log --oneline --graph --all -15

# 2. Drop a bookmark on the current state; branches are free
$ git branch backup/before-rescue

# 3. Got uncommitted changes you care about? Commit or stash them first
$ git stash push -u -m "before rescue"

    Your most important safety net is the reflog, a local diary of every position HEAD and each branch has pointed to. If you can find a state in the reflog, you can go back to it.

    How to name a commit

    ~ walks backwards along the first parent only, which is the history a straight line of work would have. ^ picks a parent by number, and the number only matters on a merge. HEAD@{n} is not a parent at all. It is an entry in the reflog, the diary of where HEAD used to be.

    HEAD
    Where you are now. Usually a branch name. In detached HEAD it is a commit directly.
    HEAD~2
    Two first-parent steps back. On a straight line, the commit two before the tip. HEAD~~ is the same thing.
    HEAD^2
    The second parent of HEAD. Only a merge commit has one. HEAD^ and HEAD^1 are the first parent, which equals HEAD~1.
    HEAD@{2}
    Where HEAD was two moves ago, from git reflog. Not the grandparent commit. main@{yesterday} is the same idea with a date.
    @ and @{u}
    @ is short for HEAD. @{u} is the upstream of the current branch, usually origin/main or similar.
    --
    End of options. git restore --source=HEAD~1 -- app.js will not treat app.js as a flag even if a file is named -w.

    Most "I broke it" moments are one of these. The destructive rows throw away uncommitted work in tracked files. Commits you merely move off a branch stay in the reflog for weeks. Full recipes are in Undoing things and Rescue recipes.

    Throw away unstaged edits to a tracked filegit restore <file>Those edits are gone. The staged copy is kept.
    Unstage a file, keep the editsgit restore --staged <file>Same as the older git reset HEAD <file>.
    Fix the last commit, not yet pushedgit commit --amendRewrites that commit. Do not amend a commit others have.
    Uncommit, keep everything stagedgit reset --soft HEAD~1Branch pointer only. Working tree untouched.
    Uncommit, keep the edits unstagedgit reset HEAD~1Default mode is --mixed.
    Discard local commits and editsgit reset --hard <sha>Uncommitted tracked edits are destroyed. Commits remain in the reflog.
    Make my branch match the remotegit reset --hard @{u}Same destruction. Fetch first so @{u} is current.
    Undo a commit that is already pushedgit revert <sha>Safe. Ships a new commit that is the inverse.
    Undo a merge commitgit revert -m 1 <sha>-m 1 keeps the first parent: the branch you merged into.
    I am mid-merge, mid-rebase, or mid-cherry-pick and I want outgit merge --abortAlso git rebase --abort and git cherry-pick --abort.
    I lost a commit or a branchgit reflogThen git switch -c rescue <sha>. Do not reach for --hard until you have a name pointing at it.
    Three commands that delete work

    git reset --hard overwrites tracked files. git clean -fd deletes untracked files and directories. git push --force (without --force-with-lease) can erase teammates' commits on the remote. None of these ask twice.

    Identity and configuration

    git config --global user.name "Ada Lovelace"Name stored in every commit you create.
    git config --global user.email "ada@example.com"Email stored alongside it. Not verified by Git itself.
    git config --global init.defaultBranch mainNew repositories start on main.
    git config --global core.editor "code --wait"Program Git opens for commit messages and interactive rebase. --wait matters for graphical editors.
    git config --global pull.ff onlyMake git pull refuse to create a surprise merge commit. Use pull.rebase true instead if you prefer to rebase when you pull.
    git config --global core.autocrlf inputmacOS and Linux. On Windows, Git for Windows sets true. See line endings.
    git config --list --show-originEvery setting and the file it came from: system, global, or this repo.
    git help switchFull manual. git switch -h is the short one-screen summary.

    Create and clone

    git init -b mainCreate a repository in the current directory, default branch main.
    git clone <url>Copy a remote repository, including its history, and check out the default branch.
    git clone <url> <dir>Use a different folder name than the repository name.
    git clone --filter=blob:none <url>Partial clone: commit history now, file contents on demand. --depth 1 is shallower and harder to work with later.

    The daily loop

    git statusBranch, staged changes, unstaged changes, untracked files.
    git status -sbCompact form, plus ahead/behind relative to the upstream.
    git add <file>Copy the working-tree version of a file into the index (the next commit).
    git add -pStage hunk by hunk. The way to split a messy working tree into clean commits.
    git add -AStage every change in the repo: modifications, deletions, and new files. git add . is the same from the repo root.
    git restore --staged <file>Take a file back out of the index. Does not discard your edits.
    git commit -m "Fix crash when the cart is empty"Record the index as a new commit. Omit -m to write the message in your editor.
    git commit -vOpen the editor with the diff underneath the message, so you describe what you see.
    git commit --amendReplace the tip commit with a new one. Add --no-edit to keep the message. Dangerous once pushed.
    git commit --allow-empty -m "Trigger CI"A commit with no file changes. Rare. Useful to rerun a pipeline.

    See what changed

    git diffWorking tree versus the index. What is not yet staged.
    git diff --stagedIndex versus HEAD. Exactly what the next commit will record.
    git diff HEADWorking tree versus the last commit, staged and unstaged together.
    git diff --statFiles and line counts only. Add --name-status for A/M/D.
    git diff main..featureTip of main versus tip of feature. For diff, two dots means the two endpoints.
    git diff main...featureMerge base versus feature. This is the pull-request diff: only what the branch itself changed.
    git diff -- src/Limit a diff to a path. The -- keeps the path from being read as a revision.
    git show <sha>:<file>Print a file as it was in that commit, without checking anything out. git show <sha> alone is the commit's message and diff.
    Two dots, two meanings

    git log main..feature is a set of commits. git diff main..feature is just the two snapshots. If a branch diff is full of changes you never made, switch the diff to three dots. Details in comparing commits.

    Branches

    git switch -c <branch>Create a branch at HEAD and switch to it. Older form: git checkout -b <branch>.
    git switch <branch>Move HEAD to an existing branch. Refuses if that would overwrite local edits.
    git switch -Jump back to the branch you were on before this one.
    git switch --detach <sha>Look at an old commit without moving a branch. Make a branch before you commit, or the new commits will be left dangling.
    git branchLocal branches. The starred one is HEAD. -a includes remotes, -vv shows upstream and ahead/behind.
    git branch -m <new-name>Rename the branch you are on.
    git branch -d <branch>Delete a merged branch. Git refuses if it is not merged.
    git branch -D <branch>Delete even if unmerged. The commits stay in the reflog for a while.
    git switch -c <branch> <start>Branch from a specific commit, tag, or other branch instead of from HEAD.

    Merge, rebase, and conflicts

    git merge <branch>Bring <branch> into the branch you are on. Fast-forwards when it can.
    git merge --no-ff <branch>Always record a merge commit, even when a fast-forward was possible.
    git merge --ff-only <branch>Update only if it is a clean fast-forward. Otherwise stop and let you decide.
    git merge --squash <branch>Stage the combined changes and stop. You make the commit yourself, with one parent.
    git merge --abortGive up a conflicted merge and return to the pre-merge state.
    git rebase mainReplay the current branch's commits on top of main. Rewrites them. Never do this to shared history.
    git rebase --continueAfter you have fixed and staged a conflict. --skip drops this commit. --abort restores the branch as it was.
    git rebase -i HEAD~3Edit the last three commits: reorder, squash, reword, drop. Only on commits nobody else has.
    git rebase --onto main old-base featureReplay onto main only the commits that feature has beyond old-base.
    git restore --source=HEAD -- <file>During a merge, HEAD is "ours" (the branch you are on). git restore --source=MERGE_HEAD -- <file> takes "theirs". During a rebase those words are swapped: see conflicts.
    git diff --checkReport leftover conflict markers and whitespace errors before you commit.

    Remotes and collaboration

    git remote -vRemote names and their fetch/push URLs.
    git remote add origin <url>Name a remote. origin is only a convention.
    git fetch --pruneDownload new remote commits and delete remote-tracking branches whose upstream is gone. Does not touch your files.
    git pullFetch, then integrate the upstream into your current branch (merge, or rebase if you configured that).
    git pull --rebaseFetch, then rebase your local commits on top of the upstream.
    git pushUpload the current branch to its upstream. Fails if the remote has commits you do not have.
    git push -u origin HEADPush the current branch and set its upstream, even if the names differ.
    git push --force-with-leaseOverwrite the remote branch only if it still points where you last fetched. The safe force-push after a rebase of your own branch.
    git push origin --delete <branch>Delete a branch on the remote. Does not delete your local branch.
    git remote prune originDrop stale remote-tracking refs without a full fetch. git fetch -p does both.
    git branch -u origin/<branch>Set the upstream of the current branch after the fact.

    Undo in command form

    git restore <file>Danger. Replace a tracked file's working copy with the staged version (or HEAD, if you have not staged it).
    git restore --source=HEAD~1 -- <file>Copy a file from an older commit into the working tree. Add --staged as well if the index should match.
    git reset --soft HEAD~1Move the branch back one commit. Index and files stay as they were, so the changes remain staged.
    git reset HEAD~1Move the branch back and unstage. Your edits stay in the working tree.
    git reset --hard HEAD~1Danger. Move the branch back and overwrite tracked files. Uncommitted edits are not in the reflog.
    git reset --keep <sha>Like a careful hard reset: refuses to run if it would overwrite local changes.
    git revert <sha>New commit that undoes <sha>. The right tool on a shared branch.
    git revert -m 1 <merge-sha>Revert a merge. -m 1 means "the first parent is the mainline to keep".
    git reflogEvery recent move of HEAD. The way back after a reset, rebase, or deleted branch.
    git reset --hard ORIG_HEADRight after a reset or merge, ORIG_HEAD is where you were. Later than that, use a reflog hash instead.
    git clean -ndPreview deletion of untracked files and directories. Drop the n (git clean -fd) only when the list is what you mean. -x also deletes ignored files.
    git stash push -m "wip: search"Shelve uncommitted work, including staged state. -u also stashes untracked files. Restore with git stash pop.

    Read history

    git log --oneline --graph --decorate --allThe picture of every branch. Drop --all for the current branch only.
    git log -p -3The last three commits with their full diffs.
    git log main..featureCommits reachable from feature but not from main. What the branch would add.
    git log --left-right main...featureCommits on either side since they diverged. < is main, > is feature.
    git log @{u}..Commits you have not pushed. git log ..@{u} is commits you have not pulled.
    git log -S"priceFor"Commits that changed the number of occurrences of a string. -G"regex" matches a diff against a pattern.
    git log --follow -- src/cart.jsHistory of one file, across renames.
    git blame -w -L 40,60 src/cart.jsWhich commit last touched each line. -w ignores whitespace-only changes.
    git bisect startThen git bisect bad and git bisect good <sha>. Git checks out the midpoint until you find the bad commit. git bisect reset returns you home. git bisect run ./test.sh automates it.
    git grep -n "priceFor"Search tracked files. Add a revision (git grep priceFor v1.2.0) to search the past.
    git shortlog -snCommit counts by author.

    Rewrite before you share it

    git commit --fixup <sha>A commit labelled to fold into <sha>. Finish with git rebase -i --autosquash <sha>~1.
    git cherry-pick <sha>Copy one commit onto the current branch as a new commit. --abort if the conflict is not worth it.
    git cherry-pick main..featureCopy a series. The range is the same set git log would show.
    git rebase --abortAbandon an in-progress rebase. After a finished rebase you regret, git reset --hard ORIG_HEAD.
    The golden rule, in one line

    Do not rebase, amend, or filter-branch commits that other people already have. If you rewrote your own already-pushed feature branch, update it with git push --force-with-lease, and only if nobody else built on it. See merge versus rebase.

    Stash, tags, and worktrees

    git stash listEverything you have shelved. git stash show -p stash@{1} prints one of them.
    git stash popApply the newest stash and delete it if the apply succeeded. apply keeps the stash. drop throws one away (recoverable from the reflog of the stash).
    git tag -a v1.4.0 -m "Release 1.4.0"An annotated tag on HEAD. Lightweight tags (git tag v1.4.0) are just a name, with no message or tagger.
    git push origin v1.4.0Tags are not pushed with the branch. git push --follow-tags pushes annotated tags that are part of the commits you are pushing.
    git worktree add ../hotfix hotfixA second working directory with hotfix checked out, sharing the same .git. Remove it with git worktree remove ../hotfix.
    git worktree listEvery checkout attached to this repository.

    Files, renames, and ignore rules

    git rm <file>Delete a tracked file and stage the deletion.
    git rm --cached <file>Stop tracking a file without deleting your copy. The usual follow-up to adding it to .gitignore.
    git mv old newRename or move, and stage it. Git detects renames after the fact anyway. This just stages both halves at once.
    git check-ignore -v <file>Which ignore rule, in which file, is matching this path. Essential when a file will not go away or will not be added.
    git update-index --skip-worktree <file>Tell Git to leave a tracked file alone locally (for example a config you must edit). Fragile. Prefer a template file such as config.example when you can.

    When it is already wrong

    git switch correct-branchIf the commit is only on the wrong branch and that branch is one commit ahead: git switch wrong, git reset --soft HEAD~1, git switch correct, git commit. Step by step in committed to the wrong branch.
    git switch -c rescueYou committed in detached HEAD. This pins a branch to those commits before you leave.
    git switch -c <branch> HEAD@{1}Recreate a just-deleted branch from the reflog. Find the right entry with git reflog first.
    git fetch originThen git reset --hard origin/<branch> to make the local branch identical. Danger: local commits and uncommitted edits on tracked files are discarded (commits stay in the reflog).
    git pull --rebaseWhen you and the remote both added commits. Rebase if the local commits are yours alone. Merge if the branch is shared.
    git rm --cached .envStops the next commit from tracking it, and is not enough. A secret that was pushed is compromised: rotate it, then purge history. See pushed a secret.
    git fsck --lost-foundFind commits no branch points at, after the reflog is no help. Recovered objects land in .git/lost-found/.
    ssh -T git@github.comTest the key GitHub (or your host) is seeing. The Git-side fix is almost always the remote URL or ssh-add, not a Git command. See publickey.

    Reading a short status

    git status -sb prints two columns. The left is the index, the right is the working tree.

    Check yourself

    What is the difference between HEAD~2 and HEAD^2?

    HEAD~2 walks two steps along first parents: the grandparent on the main line. HEAD^2 is the second parent of the current commit, which exists only when HEAD is a merge. On an ordinary commit, HEAD^2 is an error, while HEAD~2 is just two commits back.

    A bad commit is already on origin/main and your teammates have pulled it. Which command do you use?

    git revert <sha>, then push the new commit. git reset would rewrite published history and force everyone else to repair their clones. If the bad commit is a merge, add -m 1 so Git knows which parent is the mainline.

    Why does git diff main..feature show changes you never made on feature?

    For git diff, two dots compare the two tips directly. Commits that landed on main after you branched appear as the reverse of those commits. git diff main...feature compares the merge base with feature, which is the pull-request view. The same two-dot syntax in git log means something else: a set of commits, not a pair of trees.

    You amended a commit and only then remembered it was already pushed. What is the honest repair?

    The amend replaced the commit with a new hash, so your branch and the remote have diverged. If nobody else has built on the old commit, git push --force-with-lease updates the remote and still refuses if someone else pushed in the meantime. If the branch is shared, do not force-push: check the old hash out of the reflog, put the branch back, and use git revert or a new commit instead.
